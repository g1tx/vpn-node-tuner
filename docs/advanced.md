# VPN Node Tuner — подробная настройка

Тюнер Linux для небольших exit-нод Xray / VLESS + REALITY + TCP. Основной сценарий — Ubuntu 24.04, 1 vCPU, 1–2 ГБ RAM, около 30 активных пользователей со смешанным трафиком. Цель — высокая полезная скорость и быстрый отклик под нагрузкой.

Профиль `balanced` по умолчанию сохраняет текущий алгоритм TCP и поддерживаемые очереди `fq`/`fq_codel`, включает pacing для `fq` и ограниченно настраивает буферы. Профиль `bbr` явно включает BBR и `fq`. Скрипт работает с **действующей** очередью интерфейса, сохраняет изменения после перезагрузки и позволяет восстановить исходное состояние. Пакеты устанавливаются оператором. Постоянного процесса тюнера нет: systemd запускает короткий oneshot-скрипт очередей при загрузке.

## Быстрый старт

```bash
curl -fsSL https://raw.githubusercontent.com/g1tx/vpn-node-tuner/main/tune.sh -o tune.sh
bash tune.sh --diagnose
bash tune.sh --dry-run
sudo bash tune.sh --apply

# BBR + fq — отдельный вариант для сравнения на вашем маршруте.
sudo PROFILE=bbr bash tune.sh --apply
```

Зависимости: Bash 5+, `iproute2` (`ip`, `tc`), `procps` (`sysctl`), `util-linux` (`flock`), GNU coreutils, systemd и `systemd-analyze` (из пакета systemd). Основная проверенная ОС — Ubuntu 24.04 со штатным ядром 6.8. На других системах сначала изучите предварительный просмотр; наличие нужных параметров и очередей проверяется до применения.

Универсально лучшего алгоритма TCP нет: BBR может уступать CUBIC по скорости или задержке на конкретной нагрузке. Сравнивайте одинаковый трафик и маршрут до выбора профиля. `sudo bash tune.sh --apply` использует `PROFILE=balanced`; явный `PROFILE=bbr` требует доступного BBR и применяет `fq`.

```bash
# Укажите бюджет канала и характерный RTT клиентов, если они известны.
# Скорость виртуальной сетевой карты не равна доступной скорости в Интернет.
sudo BANDWIDTH_MBIT=1000 BDP_RTT_MS=60 bash tune.sh --apply

# Для выбора другого интерфейса сначала выполните откат.
sudo NIC=eth0 bash tune.sh --apply

# Исходное состояние сохраняется при первом применении и не затирается повторными.
sudo bash tune.sh --revert
```

## Что меняется

| Настройка | Поведение |
|---|---|
| TCP congestion control | `balanced` сохраняет текущий алгоритм. `bbr` проверяет BBR и при необходимости загружает `tcp_bbr`. Ошибка не маскируется успешным итогом. |
| Очереди интерфейса | `balanced` сохраняет `fq_codel` и настройки `fq`, включая pacing для `fq`. Поддерживаемая FIFO заменяется на `fq` при текущем BBR, иначе на `fq_codel`. `bbr` применяет `fq` с pacing. Корень `mq` сохраняется. |
| Буферы | Целевой максимум `min(2 × BDP, RAM / 32, 16 МиБ)`; большие существующие максимумы сохраняются. Минимальные и начальные TCP-буферы сохраняются. |
| TCP receive autotuning | Включается. |
| MTU probing | Обнаружение TCP MTU black hole (`tcp_mtu_probing=1`). |
| Native Xray systemd | Поднимает soft/hard `LimitNOFILE` установленной службы минимум до 65536, сохраняя большие значения. Шаблоны `*@.service` пропускаются: эффективные лимиты их экземпляров неизвестны. Изменение лимита действует после следующего перезапуска службы оператором. |
| Персистентность | Собственный sysctl drop-in и systemd-служба очередей с повторным применением при каждом запуске тюнера. |

`BANDWIDTH_MBIT=1000` и `BDP_RTT_MS=100` — явно обозначенные предположения по умолчанию. Это не результаты измерения. Для 1 ГБ RAM при этих значениях целевой максимум сокетного буфера — 16 МиБ. Максимум допускает рост по потребности и не выделяется сразу для каждого соединения. Один пользователь обычно создаёт много соединений.

В профиле `bbr` BBR становится алгоритмом по умолчанию для новых TCP-сокетов. Уже открытые соединения и сокеты, для которых приложение явно выбрало другой алгоритм, могут его сохранить. Само изменение default не требует безусловного перезапуска приложения; тюнер не перезапускает службы автоматически.

Повторное применение и смена профиля сохраняют первый снимок для `--revert`. Профиль `balanced` сохраняет текущее состояние и не отменяет ранее включённый BBR. Чтобы вернуть состояние перед первым применением, используйте `--revert`. Для `net.core.default_qdisc` профиль `balanced` сохраняет существующие `fq`/`fq_codel`, иначе выбирает ту же замену FIFO.

Приоритет — сохранить работающие настройки системы. Общие `tcp_mem`/`udp_mem`, IPv6, маршрутизация, firewall, ECN, VM/IO, conntrack, offload-функции, RPS/XPS, размер аппаратных колец и `txqueuelen` автоматически не меняются. На 1 vCPU распределение обработки между ядрами не даёт выигрыша. Произвольные большие очереди могут увеличивать задержку; отключение GRO/TSO может повысить загрузку CPU.

Перед изменением runtime-параметров тюнер читает итоговую конфигурацию через `systemd-analyze cat-config sysctl.d`. Если более поздний конфиг переопределяет управляемый параметр, применение откатывается с указанием конфликта. Это предотвращает ситуацию, когда после reboot возвращается другое значение.

Сложная конфигурация `tc`, неизвестные параметры или ingress/clsact требуют ручной проверки: тюнер завершится до применения, сохранив существующую схему. Скрипт не добавляет ограничитель скорости. Если очередь находится у провайдера или на клиентском роутере, локальный `fq` не гарантирует низкую задержку при насыщении этого участка.

## Docker / Remnawave

`--diagnose` показывает сетевой режим и назначенные лимиты контейнеров. В режиме `host` контейнер использует сетевой namespace хоста; при `bridge` часть TCP-настроек хоста может не действовать внутри контейнера. Не меняйте сетевой режим существующей ноды без проверки портов и конфигурации панели.

Тюнер не перезапускает Docker и не переписывает `daemon.json`. Docker defaults не меняют уже созданные контейнеры. Лимиты следует задавать в конфигурации ноды/Compose и применять её штатным способом. Пример для проверки вашей существующей конфигурации:

```yaml
services:
  remnanode:
    # image, environment, volumes и остальные параметры — из инструкции панели
    network_mode: host
    ulimits:
      nofile:
        soft: 65536
        hard: 65536
    logging:
      driver: json-file
      options:
        max-size: '10m'
        max-file: '3'
```

На стороне Xray проверьте согласованность `xtls-rprx-vision` на сервере и клиенте, настройки DNS/маршрутизации, избыточные access-логи, CPU throttling и лимит памяти контейнера. Тюнер ядра не исправляет эти настройки автоматически. TCP Fast Open требует поддержки со стороны приложения и клиента; один sysctl не гарантирует сокращения времени соединения.

## Откат и переход со старой версии

Состояние хранится в `/var/lib/exit-node-optimizer` с доступом только root. Сохраняются изменяемые файлы, исходные runtime sysctl, конфигурация поддерживаемых очередей и состояние служб. Перед каждым повторным применением создаётся отдельная точка восстановления на случай ошибки. При неполном откате скрипт сохраняет снимок и сообщает об ошибке. Если при применении потребовалось загрузить модуль `tcp_bbr`, откат оставляет его загруженным: принудительная выгрузка может затронуть действующие соединения, а исходный алгоритм восстанавливается.

`--revert` возвращает состояние **перед первым применением этой версии**. Это не сброс всей Ubuntu к заводским настройкам. Счётчики пакетов и автоматически выданный kernel handle очереди могут отличаться после её восстановления; восстанавливаются параметры и место подключения очереди. Служба native Xray должна быть перезапущена оператором, чтобы изменение лимита вступило в силу.

Старая версия этого репозитория меняла больше параметров, выключала IPv6 и могла менять Docker. Новая обнаруживает её файлы и требует явного перехода:

```bash
sudo bash tune.sh --apply --migrate-legacy
```

Переход сохраняет старые файлы для отката и убирает старую персистентную настройку. Уже применённые старые VM/IPv6/NIC-параметры и настройки Docker остаются до отдельного восстановления. Изучите старые Docker-бэкапы `daemon.json.xray.bak.*`; выбирать и восстанавливать их нужно вручную. Для чистой исходной точки после удаления старой персистентной настройки выполните запланированную перезагрузку, затем повторное применение. Сам тюнер сервер не перезагружает.

## Измерение результата

Проверяйте одинаковый маршрут до и после изменений: скорость передачи, медиану и p95 времени первого ответа, повторные передачи, CPU/steal, давление памяти и drops. Низкий ping в простое не показывает поведение при скачивании.

В репозитории есть отдельный `benchmark.sh`. Запускайте его **на клиенте**, чтобы включить клиентский канал и VPN в измерение. Нужны `curl` и доступные вам тестовые HTTP(S)-адреса: большой файл для загрузки и небольшой ответ для проб.

```bash
bash benchmark.sh \
  --download-url 'https://YOUR-TEST-HOST/large-file' \
  --probe-url 'https://YOUR-TEST-HOST/small-file' \
  --proxy 'socks5h://127.0.0.1:1080' \
  --parallel 4 --seconds 20 --output benchmark-before
```

После применения повторите с `--output benchmark-after`. Если VPN уже направляет системный трафик, параметр `--proxy` не нужен. Прямой запуск на сервере проверяет другой путь. Загрузки могут использовать много трафика. Скрипт сохраняет сырые результаты, считает медиану/p95 TTFB и приблизительную суммарную скорость. Ошибка HTTP/curl либо завершение любой загрузки раньше 90% заданного времени завершают тест с ненулевым кодом и сохраняют отчёт как неполный. Ограничение скорости самим тестовым адресом также нужно учитывать при интерпретации.

[Проверка на чистой Ubuntu с 30 параллельными скачиваниями](clean-host-results.md), [предыдущая лабораторная проверка и её ограничения](lab-results.md).

## Проверка разработки

```bash
bash -n tune.sh benchmark.sh
shellcheck tune.sh benchmark.sh
sudo bash tests/run.sh
```

CI запускает проверки на Ubuntu 24.04. Fixture-тесты изолируют команды и файловую систему; реальные применения, повторный запуск, откат и сохранение после перезагрузки дополнительно проверяются на тестовом VPS.

## Границы эффекта

Порт 1 Гбит/с не гарантирует гигабит полезного VPN-трафика: влияют CPU, гипервизор, маршрут, потери, клиент и ограничения провайдера. BBR и `fq` не сокращают физическую длину маршрута. Выбор более близкой ноды и исправление перегруженного участка сети иногда важнее настроек ядра. Устанавливать другое ядро ради BBRv3 автоматически скрипт не будет.
