# Проверка exit-node-optimizer — 30 октября 2026

Это историческая проверка раннего BBR/fq-профиля. Последующая [проверка чистой Ubuntu и 30 параллельных скачиваний](clean-host-results.md) привела к сохранению штатных TCP/очередей в профиле balanced по умолчанию. Результаты ниже не являются замером нынешнего профиля по умолчанию.

## Что проверялось

Тестовый VPS: 1 vCPU AMD EPYC-Rome, изначально около 2 ГБ RAM, Ubuntu 24.04, Docker/Remnawave и nginx с host networking. Сервер уже был настроен старой версией тюнера. Поэтому его начальное состояние нельзя называть чистой Ubuntu.

На старте BBR уже работал, но действующая очередь eth0 оставалась pfifo_fast, а txqueuelen был равен 5000. Старые файлы сохранены на сервере в закрытом каталоге `/root/exit-node-lab`, затем отключены. После перезагрузки txqueuelen вернулся к 1000, а общие пределы TCP-памяти снова рассчитывались ядром. Конфигурация Docker сохранена: её изменения старым тюнером автоматически не угадывались и не отменялись.

## Контролируемое сравнение TCP

На ядре 6.8.0-36 выполнено 9 опытов внутри сетевых namespaces: канал HTB 100 Мбит/с, по 20 мс netem в каждом направлении, четыре параллельных TCP-потока iperf3. Каждый опыт — 18 секунд измерения после 2 секунд разогрева; три повтора с перестановкой порядка. FIFO — pfifo с лимитом 1000, fq — с общим лимитом 1000 и лимитом потока 100. Offload-функции отключались только у экспериментальных veth; основная сетевая карта не менялась.

В таблице — медианы результатов трёх запусков, p95 рассчитан внутри каждого запуска.

| Режим | Полезная скорость, Мбит/с | Медиана ping под нагрузкой, мс | p95 ping, мс |
|---|---:|---:|---:|
| CUBIC + FIFO | 93,828 | 45,8 | 47,0 |
| BBR + FIFO | 93,788 | 42,2 | 42,6 |
| BBR + fq | 93,674 | 40,2 | 40,4 |

В этом опыте fq уменьшила добавочную задержку без существенного изменения полезной скорости. Это TCP-лаборатория на одном сервере, без шифрования и реального маршрута VPN. Результат не означает аналогичный выигрыш на любом VPS или при очереди за пределами сервера.

Данные: [controlled-tcp.json](evidence/controlled-tcp.json).

## Работа с 1 ГБ RAM

Для реальной проверки в загрузочные параметры временно добавлялся `mem=1024M`, затем сервер перезагружался. Ядру 6.8.0-147 было доступно **961,617 МиБ**. Remnawave и nginx запустились; собственная служба fq и управляемые sysctl сохранились после reboot. Использовался существующий Xray 26.7.28 в Remnawave и отдельный локальный клиент Xray 26.10.29 из официального релиза с проверенным SHA256.

Трафик шёл через действующий REALITY/Vision до публичных HTTPS-сайтов. Клиент, curl и сервер находились на одном 1-vCPU VPS: это добавляет нагрузку клиента к нагрузке ноды. Проверялось много соединений с одной учётной записью; это не равнозначно 30 людям с браузерами, десятками вкладок и разными маршрутами.

### Четыре скачивания и всплеск 30 HTTPS-запросов

Официальный ISO Ubuntu скачивался четырьмя потоками 15 секунд, каждый поток ограничен 10 МиБ/с. Во время скачивания одновременно запускались ещё 30 небольших HTTPS-запросов.

| Показатель | Результат |
|---|---:|
| Все четыре загрузки | HTTP 200, каждая длилась 15 секунд |
| Передано | 498 604 471 байт |
| Средняя суммарная скорость | 265,864 Мбит/с |
| Минимальная доступная память | 364,289 МиБ |
| OOM-kill | 0 |
| Максимально занято swap | 2,523 МиБ |
| Новые страницы, выгруженные в swap | 634, около 2,48 МиБ |
| CPU в окне загрузки, включая steal | 66,554% |
| Из них steal | 2,365% |
| Дополнительные HTTPS-запросы | 30 из 30 успешны |

Отклик при всплеске ухудшился: медиана/p95 фоновых TTFB-проб выросли с **83,04/90,23 мс** в простое до **93,40/1082,59 мс** под нагрузкой. Для самого всплеска 30 запросов медиана — 1599 мс, p95 — 1701 мс. Запас памяти сохранился, но быстрый отклик при резком массовом установлении соединений этот VPS не обеспечил.

### Повтор без всплеска запросов

В отдельном 10-секундном опыте с теми же четырьмя потоками, без дополнительного всплеска, получено 130,477 Мбит/с; минимальный MemAvailable — 417,336 МиБ, новых выгрузок в swap и OOM не было. CPU — 51,033%, из них steal — 4,442%.

Медиана/p95 TTFB под нагрузкой — **90,00/138,95 мс**. В простое этого же опыта p95 составил 1084 мс при медиане 82 мс: на WAN встречались отдельные большие задержки даже без скачивания. Различие скоростей двух опытов показывает влияние внешнего маршрута/источника. Эти замеры не определяют максимальную пропускную способность VPS и не являются сравнением «до/после» настройки при 1 ГБ.

Публичный Cloudflare speed endpoint в одной попытке вернул HTTP 403. Его результат исключён; benchmark теперь завершает такие тесты с ошибкой, а не выдаёт их за рабочую нагрузку.

Данные: [опыт со всплеском](evidence/encrypted-1g-burst.json), [опыт без всплеска](evidence/encrypted-1g-no-burst.json).

## Что это означает для VPN на 1 ГБ

**VPN-ноду на 1 ГБ RAM поднять можно.** В проверенной конфигурации Ubuntu + Docker + Remnawave-node + nginx запускались и выдержали описанные короткие опыты. В обычном простое использовалось около 440–450 МиБ, доступно было примерно 500 МиБ. Полноценную панель управления с БД и дополнительными сервисами разумнее размещать отдельно от такой маленькой ноды.

Основные ограничения:

- Количество соединений важнее числа пользователей. Браузеры, YouTube и загрузки могут создавать много сокетов и буферов; 30 активных людей не означают 30 соединений.
- Пики памяти при большом количестве соединений, обновлении контейнера, загрузке списков маршрутизации и логировании могут закончиться OOM и перезапуском процесса. Короткий тест не заменяет длительное наблюдение.
- Swap может помочь пережить нехватку RAM, но обращения к SSD увеличивают задержку. В проверке активное небольшое вытеснение появилось только в более тяжёлом опыте.
- Одно виртуальное ядро обрабатывает шифрование, TLS-рукопожатия и сетевой стек. Очередь CPU и steal гипервизора могут ухудшать отклик даже при свободной памяти.
- Гигабитный порт не гарантирует гигабит VPN: влияют маршрут, потери, политика провайдера, клиент и CPU. Проверенные 266 Мбит/с не являются ни потолком ноды, ни обещанием постоянной скорости.
- Для SSD 15 ГБ существенны ротация логов и объём Docker-образов. Настройки логов должны применяться к реально созданным контейнерам.

Для примерно 30 пользователей со смешанным трафиком 1 ГБ — рабочий вариант при контроле нагрузки, но запас небольшой. Более высокая RAM даёт запас для пиков; задержка также зависит от CPU и сети. Следить стоит за MemAvailable, memory pressure, swap-in/out, OOM, CPU/steal, retransmits и p95 времени ответа.

## Проверки реализации

Проверены применение, повторное применение, восстановление исходных runtime-значений и файлов, сохранение после reboot, загрузка при ограничении RAM до 1 ГБ. Отдельные изолированные тесты проверяют валидацию ввода, mq, пользовательские фильтры tc, миграцию старых файлов, отказы sysctl/сервисов/копирования снимка, конкурирующий запуск и конфликты приоритетов sysctl.d. HTTP-тесты benchmark проверяют успешную загрузку, HTTP 403, слишком короткий файл и остановку дочерних загрузок при отмене.

После опыта временное ограничение RAM удалено; очередная перезагрузка подтвердила возврат исходных 2 ГБ. На сервере остаётся проверенная настройка новой версии; приватные тестовые клиентские конфиги и временный SSH-ключ удалены. Финальные 23 теста тюнера и 4 HTTP-теста прошли на VPS; Bash syntax и ShellCheck также прошли. После последнего reboot запрос через действующий REALITY/Vision получил HTTP 200.
